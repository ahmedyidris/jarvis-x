4. The Agentic OS layer — self-maintenance and continuous
improvement
This is the part of your request that’s new: turning Jarvis X into a system that checks and
repairs itself, not just a system you debug by hand each session.

4.1 Two loops, borrowed from the bitemporal-memory pattern you were just
reading
The memory-repair architecture you reviewed (arrival path + sweep path converging on one
writer) generalizes directly to project health, not just to conversational facts:

                                 Arrival path (event-driven)      Sweep path (time-driven)
 In the memory guide             User says something →            Timer fires → detect drift
                                 extract → classify → repair      nobody reported → propose
                                                                  → repair
 Applied to Jarvis X itself      You (or Claude Code) make a      A scheduled jj status --
                                 change → tests run →             deep run finds rot nobody
                                 AS_BUILT.md updates              reported: a dependency that
                                                                  silently stopped being used, a
                                 Arrival path (event-driven)     Sweep path (time-driven)
                                                                 test that quietly stopped
                                                                 asserting anything, a doc that
                                                                 drifted from the code

The same asymmetry applies: a broken build is easy to notice — CI turns red. A stale-but-
passing check (like the 17 file-existence “milestones” that stayed green through an actual jail-
escape bug) is the dangerous case, because nothing signals it. That is precisely what the Sept 3
triage found, and it’s worth building a permanent defense against rather than re-discovering it
every few weeks.

4.2 Concrete self-maintenance mechanism to build
  1.   A repairs-style audit table for the repo itself, not just for memory — every
       automated fix Claude Code proposes gets one append-only row: what changed, why,
       evidence, confidence, who approved it. You already have the human-approval gate in
       your operating rules; this just gives it a permanent, queryable log instead of scattered
       session summaries.
  2.   A weekly (not per-session) sweep, run on a schedule via the existing scheduler
       component (already 8/8 tested): re-run the JS suite, re-run model-gateway tests, check
       for tests with zero assertions (the test-guard.js / test-shell.js failure mode),
       and diff AS_BUILT.md’s claims against fresh command output. Anything that drifted
       gets parked for your review — this reuses the gate/inbox pattern from the memory
       guide almost exactly.
  3.   Confidence-gated auto-apply, never autonomous merge. Per your standing rule
       (Claude Code as reviewed diff proposer only): routine, low-risk fixes (a missing
       dependency, a stale version pin) can be proposed with a diff and auto-flagged high-
       confidence; anything that deletes, disables, or changes the constitution always parks for
       your explicit approval — mirroring the memory guide’s two-threshold routing (0.80 to
       retire something, 0.60 to only add something).
  4.   One evidence file, always current: AS_BUILT.md stays the single source of truth.
       Every status document that isn’t AS_BUILT.md gets a one-line “superseded by
       AS_BUILT.md, <date>” header the moment a newer sweep runs — this is already your
       own stated rule from the runbook; the sweep just makes it automatic instead of manual.
This gives you “self-maintaining” in the honest sense your own hardware supports: cheap, SQL-
and-file-read detection running on a timer, human-gated repair, full audit trail — not
autonomous self-modification, which stays permanently out of scope per your constitution.




5. Deployment: local on the Chromebook, and “online”
Local (Crostini): unchanged from your current setup — services run under Crostini, bound to
127.0.0.1 only. Nothing in this blueprint proposes exposing a port to the internet;
MASTER_PLAN_v3.md explicitly rejected that (0.0.0.0 binding), and it stays rejected here.
“Online” access, without exposing anything: git is the sync layer, per the runbook §7 — not
a tunnel, not a public endpoint.
cd ~/jarvis-x
git add -A && git commit -m "checkpoint: $(date -Is)" && git push

From any machine — phone, another laptop, a browser via Claude Code’s remote access — you
pull the latest commit and continue. This is the correct “online” answer for a $0-budget,
security-conscious setup: your data and models never leave the Chromebook; only code and
config sync.
