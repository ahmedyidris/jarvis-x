### Docker: from disk-blocked to running healthy
5 local `docker build` attempts on the dev machine's Crostini container all hit the same real, reproducible wall: the pip-install layer's commit step needs more disk headroom than this 35GB-allocation container has, confirmed across two different starting-disk levels (11GB and 13GB free) with identical failure points. Along the way, 3 real dependency conflicts were found and fixed (not guessed): `omnivoice` (+6 packages that existed only to support it) pinned a git commit whose current metadata requires `transformers>=5.3.0`, conflicting with this repo's load-bearing `transformers==4.42.4`; `kokoro-onnx`'s declared `numpy>=2.0.2` floor is stricter than what it actually needs at runtime (verified against the real, working `numpy==1.26.4` environment) — moved to a `--no-deps` follow-up install. `--no-cache-dir` added everywhere after confirming pip's build-time wheel cache was roughly doubling peak disk usage during that one step.

Given the local disk ceiling, the build moved to GitHub Actions (`.github/workflows/docker-build.yml`, manual dispatch, pushes to `ghcr.io/ahmedyidris/jarvis-x`) — succeeded there on the first run. Pulling the image back down locally then hit its own real issue: a flaky connection producing repeated `unexpected EOF` on specific layers, fixed by tuning `/etc/docker/daemon.json` (`max-concurrent-downloads: 2`, `max-download-attempts: 10`) rather than blindly retrying. `docker-compose up` then surfaced a genuine port conflict — this same machine's live bare-metal deployment already owns `127.0.0.1:8000` and `127.0.0.1:11434` — fixed by remapping the container to host port 8001 and dropping the (already-optional) 11434 host exposure.

End state, verified live, not assumed: container reaches `Up (healthy)`, `curl http://localhost:8001/api/status` returns real data (all TTS voices loaded — Piper, Kokoro, MMS, EGTTS), startup logs show a clean supervisord handoff with all 4 Ollama models recognized via the bind-mount (no re-download). The bare-metal `hermes-api`/`ollama` deployment's uptime was confirmed unbroken throughout every step of this — builds, pulls, a hung concurrent build that had to be killed, port remapping.

### CI (`test.yml`) fix: exec.js's BASE doesn't exist on hosted runners
A separate terminal session tried several `sed`-based fixes assuming a hardcoded `/home/runner/jarvis-x` string in `code/test-exec.js` — that string never existed there (`exec.js`'s `BASE` is already computed via `path.resolve(process.env.HOME, 'jarvis-x')`, no literal path anywhere), which is exactly why every attempted `sed` matched nothing and committed nothing. A local `npm test` reporting 11/11 passing wasn't evidence CI was healthy either — it ran all 11 tests locally, including the 5 CI intentionally excludes because they need local Ollama/Piper/Kokoro.

The actual, verified failure (via `gh run view --log-failed`, not guessed): `ENOENT: no such file or directory, lstat '/home/runner/jarvis-x'`. `exec.js`'s `BASE` is correct for the real deployment (the app genuinely lives at `~/jarvis-x` on the dev machine) but `actions/checkout` puts the code at `$GITHUB_WORKSPACE` on a hosted runner, not `$HOME/jarvis-x`. Fixed with a symlink step (`$HOME/jarvis-x` → checkout dir) rather than touching `exec.js`'s correct production logic. Also restored two things lost in that session's heredoc rewrites of the workflow file (one of which had corrupted, duplicated lines mid-paste): the `push`/PR branch scoping (had been accidentally widened to all branches) and the "why 5 tests are excluded" explanatory comments (logic was still correct, just undocumented).

Verified in a live CI run after the fix: `js-suite`, `model-gateway-suite`, and `web-build` all pass. `docker-build.yml` re-verified separately against the current repo state too — still builds and pushes cleanly (2m7s this time, courtesy of the GitHub Actions cache from the first run).
